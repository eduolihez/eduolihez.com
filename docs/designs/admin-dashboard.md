## Problem Statement

Eduardo runs eduolihez.com (portfolio) and will keep shipping side projects
(BloomGram next, more after). Each one currently lives in isolation — its own
analytics, if any, checked separately, no shared view of "how are all my
things doing." He wants one place, `admin.eduolihez.com`, that groups a
sub-dashboard per project, plus `api.eduolihez.com` so those projects
(browser extensions, standalone programs, not just websites) can report
events back to him. He also wants Claude Code to be able to read and write
into that panel directly — not just view metrics, but leave him notes.

## What Makes This Cool

Not the dashboard itself — the shared-memory layer between him and his AI
tooling. He said it directly: *"que Claude Code pueda leer Y escribir
directamente en el panel... una capa de memoria compartida entre tú y tus
herramientas de IA."* Metrics are the excuse; persistent bidirectional
infrastructure with his AI assistant is the actual point. Secondary but
real delight: opening one URL each morning and seeing the true state of
every project he's running, instead of visiting each one separately.

He also explicitly ruled out the obvious identity move — a SOC/terminal
command-center aesthetic, despite being a security analyst — in favor of
something minimal and quiet (Linear/Vercel-style). Restraint over the
expected choice.

## Constraints

- Hosting is CDMON shared PHP/MySQL, deployed by manual FTP. No Docker, no
  Node runtime in production.
- `api.eduolihez.com` will receive POSTs from external clients he doesn't
  fully control at request time (browser extensions, standalone programs) —
  real input validation and per-project auth needed from day one, not a
  "trusted internal only" assumption.
- Visual direction: deliberately NOT the portfolio's dark terminal/SOC theme.
  Minimalist, elegant (Linear/Vercel reference), not command-center.
- Audience is himself, daily use — not a public product, not a portfolio
  showpiece (that's incidental, not the goal).

## Premises

1. Build as a PHP+MySQL extension of the existing `/admin` panel's engine
   (session/auth/DB layer already working), generalized to handle multiple
   projects — not adopt an off-the-shelf tool (Plausible/OpenPanel/PostHog),
   because those assume Docker/Node self-hosting that doesn't exist here.
   — **Agreed.**
2. The "connect Claude Code" piece is a small, custom MCP server (not a
   generic REST+API-key integration), since it's single-user and MCP is the
   current standard shape for this. — **Agreed.**
3. Command-palette-driven UI (proposed in the cross-model second opinion,
   below) was considered and explicitly declined in favor of a traditional
   dashboard (cards/charts) for the first version — simpler to build and use
   day-to-day; a query layer can sit on top later without changing the data
   model.

## Approaches Considered

### Approach A: Direct extension of the current `/admin` (chosen)
Reuse the existing session/auth/DB layer as-is — one PHP codebase, not a
fork. **Naming note:** `database/schema.sql` already has a `projects` table
(the portfolio's CMS entries — Blue Team Hub, PromptMaster, etc., served by
`/api/projects.php`). The new dashboard registry is a different concept and
needs a different name — `apps` — to avoid colliding with it. Add an `apps`
table and an `app_id` column to `visits` (the existing analytics table —
already self-purges rows older than 400 days, per its own comment; the new
ingestion data follows the same convention, see Next Steps), plus
`KEY idx_app_time (app_id, visited_at)` — matching `visits`' existing
composite-index pattern (`idx_hash_time`, `idx_bot_time`) — so the
dashboard's "this app's activity in this date range" query is indexed from
day one, not retrofitted once it's slow. New telemetry from other projects
(extensions, programs) lands in a separate, generic `app_events` table
(`app_id, event_id, type, payload JSON, created_at`,
`KEY idx_app_type_time (app_id, type, created_at)`) — `visits` stays
structured because it's driven by this site's own well-known page-load
shape; `app_events` is generic because a future app can report event types
Eduardo doesn't know in advance. Both tables are read by the same
`admin.eduolihez.com` dashboard (via `server/admin/analytics.php`'s
existing query helpers, extended rather than duplicated), scoped per app.
`admin.eduolihez.com` is a new vhost pointing at that same codebase,
re-skinned (plain PHP/Tailwind, no new runtime) with an app switcher added.
`api.eduolihez.com` is one new file, `server/api/events.php`, with
per-app API-key auth, request validation, rate limiting, and a CORS
policy scoped to allow browser-extension origins. MCP deferred to phase 2.
Effort: **L** (human: ~2-3 weekends total / CC: ~8-10h). *(plan-eng-review,
2026-09-04: the outside voice correctly called M-L uncredible once the
re-skin scope tripled same-session — split into two deliveries instead of
one optimistic estimate, see Next Steps.)* Risk: Low — still one codebase,
still reusing proven auth/DB code; the added risk is time, not
architecture.

### Approach B: New, separate app; ingestion as its own service
Clean codebase outside `server/admin/`, a generic `events` table
(project_id, type, payload JSON, timestamp), each future project registered
by config instead of bespoke pages. `api.eduolihez.com` as a dedicated
service with schema validation, rate limiting, and CORS built for external
browser-extension origins from day one.
Effort: M-L (human: ~2-3 weekends / CC: ~6-8h). Risk: Medium — more ingestion
security surface to get right before anything is usable.
Rejected for v1: too much to design before there's a daily-use payoff;
revisit if/when a second real project (BloomGram) actually needs it.

### Approach C: Ingestion-first, "eat your own dog food"
Before building the pretty dashboard, make eduolihez.com itself stop reading
its analytics straight from the DB and instead report through
`api.eduolihez.com` like any other project would — so the ingestion pipe is
proven against real production traffic before anyone else depends on it.
Effort: M (human: ~1.5-2 weekends / CC: ~4-5h). Risk: Low-medium.
Rejected for v1: delays the actual "open it every morning" payoff he named
as the goal; worth reconsidering as a mid-course correction once Approach A
has a real second project connected.

## Recommended Approach

**Approach A.** It matches everything said in this session: reuses proven
code (auth/DB layer already works), ships something real this weekend, uses
real data (his own site) instead of mocks, and defers MCP until the schema
is stable — exactly the sequencing the independent second opinion converged
on too. The real risk isn't two codebases diverging (there's only one) — it's
`/admin`'s existing single-app code paths picking up ad-hoc
`if ($app === 'eduolihez')` branches instead of a clean app-scoped query
layer as multi-app logic gets bolted on. Worth a deliberate pass to route
everything through `app_id` from the start rather than special-casing the
first app.

On the "MCP should ship polished, not last" tension the cross-model read
raised: the deferral stands, but not because the write-path matters less —
because building MCP tool definitions against an `apps`/`app_events` schema
that's still being shaped means rebuilding those definitions once the schema
settles. The sequencing serves the write-path's own quality, it doesn't
deprioritize it.

## Open Questions

- Minimal `apps` table to start from: `id, slug, display_name,
  api_key_hash CHAR(64)` (SHA-256, never the raw key — same treatment as
  `visits.ip_hash`), `allowed_origins (JSON array, for CORS + server-side
  Origin check)`, `created_at, key_rotated_at`. The raw key is shown to
  Eduardo exactly once, at creation/rotation time, then never again.

  archived_at) can be added later without a rewrite since nothing else
  references this table yet.

  `created_at`). Deliberately not finalized now — see Recommended Approach's
  note on why MCP scope waits for the schema above to hold still first.
- Where the MCP server actually runs (same PHP host via a thin wrapper vs. a
  small standalone process elsewhere) — deferred with the rest of MCP scope.
  The "~150 lines of plain PHP" estimate from the cross-model read is a
  rough placeholder, not validated against real MCP transport/handshake
  requirements — revisit when Phase 2 actually starts.
- **Blocking, not just open:** confirm CDMON's shared-hosting panel actually
  supports adding `admin.` and `api.` subdomains (new vhosts / subdomain
  document roots) before Next Steps below start — if it doesn't, Next Steps
  §2-3 need a different subdomain strategy first. **Fallback if not:**
  path-based routing (`eduolihez.com/admin-v2/`, `eduolihez.com/ingest/`) or

- `admin.eduolihez.com` reusing the existing session/auth means the session

  a one-line config change, not a new auth system, but a real tradeoff worth
  naming explicitly rather than glossing over: **every** current and future
  subdomain of eduolihez.com becomes able to read the session cookie once
  widened. *(plan-eng-review, 2026-09-04: kept anyway — every subdomain of

  the actual blast radius is "things Eduardo controls," not an open

### Delivery 1 (~1 weekend)

0. **Prerequisite:** confirm in CDMON's panel that `admin.` and `api.`
   subdomains can be added (new vhosts / subdomain document roots) before
   starting anything below — see Open Questions.
1. `apps` table (`id, slug, display_name, api_key_hash CHAR(64),
   allowed_origins JSON, key_rotated_at, created_at`) + `app_id` on `visits`
   with `KEY idx_app_time (app_id, visited_at)` (`database/schema.sql`,
   same idempotent-migration convention already used in this repo, e.g. the
   `certifications`/`posts` extension pattern), **plus a backfill step**:
   existing `visits` rows get `app_id` set to the new eduolihez.com row, not
   left null. New `app_events` table (`id, app_id, event_id VARCHAR(64),
   type VARCHAR(60), payload JSON, created_at`,
   `KEY idx_app_type_time (app_id, type, created_at)`) with a
   `UNIQUE KEY (app_id, event_id)` so a retried POST from an unreliable
   client (extensions/programs, per Constraints) is silently deduplicated
   instead of double-counted — `event_id` is client-supplied (e.g. a UUID
   the extension generates once per event). `app_events` purges rows older
   than 400 days, same convention as `visits`. PHPUnit coverage for the
   migration's idempotency, matching the repo's existing `server/` test
   convention.
2. `admin.eduolihez.com` vhost on the **same** `/admin` codebase (not a
   fork) — new shared chrome (header, nav, app switcher) re-skinned in
   plain PHP/Tailwind using Tremor's component shapes as a visual
   reference, plus **one** fully re-skinned sub-dashboard: eduolihez.com,
   with real historical data, all queries routed through `app_id` from the
   start (see Recommended Approach). This is what Delivery 1's Success
   Criteria requires — the rest of `/admin` keeps its current visual style
   for now (see Delivery 2), reachable through the new app-switcher chrome
   even though its pages aren't re-skinned yet.
3. `server/api/events.php` — single ingestion endpoint.
   - Auth: `X-API-Key` header, SHA-256'd and matched against
     `apps.api_key_hash`.
   - **Origin check (defense in depth, not just CORS):** the `Origin`
     request header is validated server-side against that app's
     `allowed_origins` — exact string match only (no prefix/substring
     matching — same class of bypass as the WHATWG-parser URL-allowlist
     issue already fixed in `safeUrl()`). Mismatched or missing Origin on a
     request that includes one → `403`. This exists because CORS headers
     alone only stop the *browser* from letting extension JS read the
     response; they don't stop the request from reaching and being
     processed by the server. The API key remains the real authorization
     boundary; this is a second layer, not a replacement.
   - Request: `POST` JSON body — `{"event_id": "<client UUID>", "type":
     "<app-defined string, e.g. install|error|click>", "payload": {...}}`,
     capped at 16KB. `422` for any malformed-request case, treated
     uniformly: body isn't valid JSON at all, `event_id`/`type`
     missing/not a string, `payload` present but not a JSON object, or body
     exceeds the 16KB cap — one check, one response shape, no need for a
     separate code per malformation type.
   - Response: `202` on newly accepted, `200` on a duplicate `event_id`
     (idempotent, not an error), `401` on bad/missing key, `403` on
     Origin mismatch, `422` on malformed body (see above), `429` on
     rate-limit.
   - Rate limiting: 120 requests/minute per API key (fixed-window counter in
     MySQL), plus a coarser IP-based limit ahead of the auth check so
     repeated invalid-key attempts (which never reach the per-key counter)
     can't be used to brute-force keys or hammer the endpoint unbounded.
   - CORS: a preflight `OPTIONS` handler runs *before* the auth check (the
     browser sends it unauthenticated) and returns `204` with
     `Access-Control-Allow-Methods: POST` and `Access-Control-Allow-Headers:
     X-API-Key, Content-Type` — required because a custom header triggers a
     preflight, and without this the browser-extension use case this design
     exists for would simply fail. For both the preflight and the real
     request: match the request's `Origin` header against that app's
     `apps.allowed_origins` array and echo back only the matching value in
     `Access-Control-Allow-Origin` (never a wildcard, never the raw array —
     the header only carries one value). `allowed_origins` accepts
     `chrome-extension://<id>` and `moz-extension://<id>` schemes, not just
     `https://`.
   - `payload` is opaque, client-supplied JSON from apps not fully under
     Eduardo's control (see Constraints) — the dashboard renders it as
     escaped text only, never as raw HTML, when displaying event details.
   - Query layer reuses `server/admin/analytics.php`'s existing helpers
     (e.g. `max_count()`) and query conventions rather than inventing
     parallel SQL for `app_events` — extend those helpers if `app_events`'
     JSON-payload shape needs something they don't already do.
   - **Accepted risk, documented, not engineered around:** a transient
     MySQL failure during a POST (shared hosting hiccups happen) drops that
     one event silently — no client-side retry is required. At personal-
     telemetry scale (not billing, not audit-critical), an occasional lost
     event costs nothing worth the complexity of a retry protocol across
     every client app.
   - PHPUnit coverage for the auth/Origin-check/validation/rate-limit/
     dedup/CORS-preflight paths, matching repo convention. Planned coverage
     (plan-eng-review, 2026-09-04): valid/missing/wrong API key; allowed/
     mismatched Origin; malformed JSON, missing fields, non-object payload,
     oversized body (all → 422); duplicate `event_id`; within/over rate
     limit; migration idempotency + `app_id` backfill on `visits`. 8
     planned paths, all committed as required tests before merge.
   - Prove it end-to-end with synthetic test events (including a
     deliberately duplicated `event_id` and a preflight `OPTIONS` call)
     before anything real depends on it.

## Failure modes

| Scenario | Test? | Handling? | User-visible? | Critical gap? |
|---|---|---|---|---|
| Transient MySQL failure during POST | No (deliberate) | No retry (accepted risk) | Silent to the sending app | **No** — silent but a documented, deliberate decision (personal-telemetry stakes), not an oversight |
| Leaked API key (extension source is inspectable) | Yes (auth path) | Hash storage + `key_rotated_at` rotation | N/A until noticed | No — real mitigation in place |
| Spoofed/mismatched Origin with a stolen key | Yes (Origin-check path) | Server-side exact-match rejection (403) | Clear error to attacker, no data written | No |
| Client retries the same POST (network flake) | Yes (dedup path) | `UNIQUE KEY (app_id, event_id)` — idempotent | Gets `200` not a duplicate row | No |
| Client bursts requests | Yes (rate-limit path) | Fixed-window counter, `429` | Clear error, can back off | No |
| CDMON doesn't support new subdomains | N/A (infra, not code) | Documented fallback (path routing / Cloudflare Worker) | Blocks Next Steps §2-3 until resolved | No — flagged as blocking prerequisite, not silent |
| Session cookie invisible on `admin.` subdomain | N/A (config) | `Domain` attribute widened to `.eduolihez.com` | Would show as "logged out" on the new subdomain if missed | No — documented fix in Open Questions |

## Worktree parallelization strategy

Sequential implementation, no parallelization opportunity — every workstream
(schema migration, `admin.eduolihez.com` re-skin, `events.php`) reads or
writes the same `apps`/`app_events` schema and the same `/admin` codebase.
The migration (Next Steps §1) is a hard dependency for both the re-skin
(§2, needs `app_id` to scope queries) and the ingestion endpoint (§3, needs
`apps.api_key_hash` to authenticate). Not worth splitting across worktrees
for a single-developer weekend project at this size.
